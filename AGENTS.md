# WakeNote Agent Instructions

## GitHub Project tasks

- [wakenote Project #4](https://github.com/users/channprj/projects/4) is the source of truth for task progress. Before any implementation, documentation, test, or release work requested through a coding agent or tool (Claude Code, Codex, or another CLI or IDE agent), register the work there as GitHub Issues, then start editing. Until the issues exist, do only the read-only investigation needed to split and register the tasks, such as reading files, running tests, and `gh` read commands. If the user explicitly asks to start editing first, you may, but create the leaf issues before the first commit so every commit can reference one. Skip issues only when the user explicitly says not to create any.
- The Headatever bump, `chore(release)` commit, and annotated tag finish the leaves they release and need no leaf of their own. Register a separate leaf only for GitHub Release publication with `pnpm release:publish`.
- First search open and closed issues and board items for the same goal (`gh issue list --repo channprj/wakenote --state all --search ...`, `gh project item-list 4 --owner channprj --format json --limit 1000`). Reuse an existing issue instead of creating a duplicate.
- Run work only through leaf issues. A leaf has one independently verifiable result, a clear file or directory scope, a completion checklist, a verification method with its expected result, and links to its parent and prerequisite issues, or `없음` when there are none. Group a goal with several results under a parent issue, create each leaf as a sub-issue of that parent with `gh issue create --parent N`, and record ordering with `--blocked-by M`; for an existing issue, use `gh issue edit N --parent P --add-blocked-by M`.
- Title new issues `type: 핵심 대상 및 작업` or `type(scope): 핵심 대상 및 작업` in concise Korean noun form, such as `fix(meetings): 회의 진행 문구 수정`. Choose `feat`, `fix`, `docs`, `chore`, or another fitting type, and end with a noun such as `추가`, `수정`, `변경`, or `정리`, never a verb ending or a period.
- Write each leaf body with the sections `목적`, `범위` (included and excluded), `파일 범위`, `완료 조건` (checklist), `검증 방법` (each check with `→` and its expected result), `관계`, and `에이전트 세션`. Write a parent body with `목적`, `완료 조건` (every leaf done, plus the version bump and parity check), and `에이전트 세션`.
- Assign `channprj` unless the user names someone else. Add the label that matches the type (`feat` → `enhancement`, `fix` → `bug`, `docs` → `documentation`), leave other types unlabeled, and do not create new labels. Add CLI-created issues to the board explicitly with `gh project item-add 4 --owner channprj --url ISSUE_URL`.
- Fill the board's `Priority` and `Size` with estimates, or leave them empty when unsure. Set Status, Priority, and Size by name, for example `gh project item-edit 4 --owner channprj --url ISSUE_URL --field Status --value "In progress"`. If you use node IDs instead, look them up each time with `gh project field-list 4 --owner channprj --format json`. Do not add new fields or options.
- The `에이전트 세션` table records each session that works on the issue: role, tool and version, model ID, reasoning effort, real session ID, resume command, working path and branch, and the actual start time in KST (`YYYY-MM-DD HH:mm`). Take the values from the running tool (for Claude Code, `CLAUDE_CODE_SESSION_ID` and `CLAUDE_EFFORT`; for Codex, `CODEX_THREAD_ID`). When a value cannot be confirmed, write `확인 불가` with the reason rather than guessing. Add a row when the session, tool, model, or effort changes.
- Never paste transcripts, raw logs, or credentials into issues. Cite verification as the command you ran and a one-line result.
- Update the board Status when each event happens, not at the end, and re-read the issue's `projectItems` after every change:
  - `Backlog` while the scope is unsettled or any `--blocked-by` prerequisite has not reached `In review`. Never move a blocked leaf to `In progress`.
  - `To do` when the leaf criteria are met and every prerequisite is `In review` or `Done`, meaning its verified commits are pushed.
  - `In progress` with a start comment naming the agent, model, effort, session ID, and scope.
  - `In review` with a comment listing the changed scope and verification evidence once the leaf's commits are verified locally.
  - `Done` once those commits, the `chore(release)` commit, and the annotated `v<version>` tag are pushed and local, tracking, and live-remote parity is confirmed. One version bump may cover several leaves.
  - `Closed` for cancelled, duplicate, or replaced work.
  - A parent is `In progress` once any leaf starts and `Done` when every leaf is `Done` or `Closed`.
  - The board has no `Blocked` status. Keep the current Status and comment the cause, the unblock condition, and the next step.
- Reference exactly one leaf in every commit message with a `Refs: #N` trailer, placed with the other trailers. A leaf may span several commits, but a commit never spans two leaves. `chore(release)` commits are exempt. Do not use closing keywords such as `Closes`, `Fixes`, or `Resolves`; close issues manually as described below.
- Never close an issue without a reason, and close in this order: post the closing comment, close the issue, then set the Status and re-read `projectItems`. The board's `Item closed` and `Auto-close issue` workflows otherwise change the Status or close the issue on their own. For `Done`, comment `## 완료` listing each completion condition with its evidence, such as the commit hash and the `v<version>` tag that contains it, then run `gh issue close N --reason completed`. For `Closed`, comment `## 종료 — <사유>`, then run `gh issue close N --reason "not planned"` or `gh issue close N --duplicate-of M`. Keep the comment, close reason, and board Status consistent.
- A new session resumes from the board, the issue bodies and comments, and the actual Git and test state. Fix any mismatch in the issues and board before continuing, and do not redo a leaf that is already done.

## Local releases

- GitHub Actions is disabled at the repository level to avoid hosted build and release costs. Keep it disabled; adding or enabling hosted workflows requires an explicit user request.
- `pnpm release:publish` reuses local artifacts matching the current commit, version, architecture and checksums, or builds them first. Commit synchronized versions before building. Use `pnpm release:build` to prepare artifacts separately; both build paths produce a DMG, checksums, and source-commit metadata under the ignored `release/` directory for the current Mac's architecture.
- Push the branch and annotated version tag, then validate publication with `pnpm release:publish --dry-run`. Dry-run reports whether a build is needed without building or publishing. Use `pnpm release:publish` when GitHub Release publication is requested, or `pnpm release:publish --draft` when a draft is requested. Automatic rebuilds preserve replaced local output under `.previous-*` directories; publication never pushes Git refs or overwrites existing GitHub releases.
- The current macOS packaging path uses ad-hoc signing and does not notarize the app. Do not describe artifacts as Developer ID signed or notarized.

## Versioning

- Every repository update must include a Headatever patch-version bump. This applies to code, tests, documentation, configuration, assets, and this file itself.
- Follow Headatever's `head.yymmdd.patch` rules: increment the patch on the same local date, reset it to `0` on a new local date, and change the head only when the user explicitly requests a major bump.
- Use the installed `headatever` skill and its bundled `scripts/headatever.sh`; never edit `VERSION` by hand.
- Before creating the release commit or annotated `v<version>` tag, synchronize the same version across `VERSION`, `package.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, and `src-tauri/tauri.conf.json`.
- Keep the functional update and its release/version metadata in separate Conventional Commits. Push the branch and annotated tag, then verify local, tracking, and live-remote parity before declaring the update complete.
- In this repository, invoking `git-commit-push-realtime` (`/gcpr`, `$gcpr`) also authorizes a release, overriding the skill's default that releases need a separate request. Once the completion audit passes and the last checkpoint is pushed, cut one release covering every pushed checkpoint that no `v<version>` tag contains yet: bump the patch with `headatever`, synchronize the version files, commit `chore(release): v<version>`, create the annotated `v<version>` tag, push the branch and the tag, and confirm local, tracking, and live-remote parity for both. Stage only the version changes, leaving other uncommitted work out of the release commit. If the run stops early, still release the checkpoints already pushed, unless a push was rejected or the branch diverged. The release ends at the tag push; GitHub Release publication still needs its own request.
